# 지시서 03 — IPS 규칙 설정 + 분기 인출 판단 엔진 + 의사결정 로그

- 프로젝트: 은퇴포트폴리오 AI (retirement-portfolio-ai.vercel.app)
- 스택: React(Vite) + FastAPI(Vercel experimentalServices) + Supabase(서버 전용 키, 전체 RLS)
- 실행: Claude Code 단일 세션 (서브에이전트 사용 안 함)
- 참조: `docs/withdrawal-system/00_design.md` 4.2, 4.7, 4.8, 4.10절만 참고 (범위 밖 기능은 구현하지 않는다)
- 선행 조건: 지시서 02가 main에 병합된 상태. main에서 `feature/decision-engine` 브랜치를 만든다.

---

## 1. 목적

분기 초에 앱을 열면 다음 질문에 답을 받는다.

> "이번 분기 생활비는 어디서 지급하고, 1버킷을 보충해야 하는가? 보충한다면 어떤 자산을 얼마나 팔아야 하며, 근거가 되는 규칙은 무엇인가? 할 일이 없다면 왜 유지인가?"

구성은 세 가지다.
1. **규칙 설정 화면**: `ips_rules`의 임계값을 사용자가 수정한다.
2. **분기 판단 엔진**: 결정론적 규칙으로 지급·보충·유지를 판단하고 근거를 반환한다.
3. **의사결정 로그**: 판단을 기록하고, 실제 실행 여부와 다르게 실행한 사유를 남긴다.

엔진은 **판단과 근거 제시까지만** 한다. 매매 실행, 자산 잔액 변경, 인출 기록 생성은 하지 않는다.

## 2. 이번 지시서에 반영된 결정 사항 (02 미해결 사항 정리)

| # | 사안 | 결정 |
|---|---|---|
| 1 | 생활비 원천 이원화 | 판단 엔진은 `cashflow_items`(02의 순인출 필요액)만 사용한다. 기존 `user_config.user.monthly_expense`와 기존 대시보드 지표는 이번에 변경하지 않는다(통합은 별도 과제). |
| 2 | 버킷 기준 이원화 | 엔진은 **실효 버킷**(재지정값, 없으면 `BUCKET_MAP`)을 쓴다. 자산군 비중 판정(R-03)은 기존 리밸런싱과 같은 **자산군 체계**를 쓴다. 버킷은 생활비의 시간 축, 자산군은 비중이라는 서로 다른 관점이므로 통합하지 않는다. |
| 3 | income의 기본 버킷 | `BUCKET_MAP` 변경 없음. 필요하면 자산별로 재지정한다. |
| 4 | R-03 허용 폭 | 두 가지 방식을 지원한다. `mode: "config"`(기본값, 기존 `rebalance_threshold` 공통값 사용)와 `mode: "relative"`(목표 비중 × `relative`, 단 최소 `min_abs`). 기본값을 `config`로 두어 현재 동작을 바꾸지 않는다. |
| 5 | 가드레일 현재 상태 | 운영 데이터는 `lower_breach`이며, 원인은 자산 증가로 확인됐다. 엔진은 증액 여지를 **참고로만** 표시하고 인출액을 자동으로 늘리지 않는다. |
| 6 | 시장 국면(R-04) | 시장 데이터 수집은 04 범위다. 이번에는 **사용자가 판단 실행 시 기준지수의 고점 대비 하락률을 직접 입력**한다. A단계에서 기존 데이터로 계산 가능한지 조사한다. |

## 3. 진행 방식 (단계별 중단점)

각 단계가 끝나면 **작업을 멈추고 보고한 뒤 사용자 승인을 받아 다음 단계로 넘어간다.**

| 단계 | 내용 | 끝나면 |
|---|---|---|
| A | 작업 전 조사 (4장), 코드 수정 없음 | 보고 후 중단 |
| B | R-03 파라미터 마이그레이션 SQL 작성 (필요 시) | SQL 보고 후 중단, 적용은 사용자 |
| C | 판단 엔진 순수 함수 + pytest (5장) | 보고 후 중단 |
| D | API: 규칙 수정, 판단 실행, 로그 (6장) | 보고 후 중단 |
| E | 화면: 규칙 탭, 분기 인출 판단 화면 (7장) | 보고 후 중단 |
| F | 자체 검증 (10장) + 최종 보고 (11장) | 종료 |

**Git 규칙**: 단계마다 커밋. main 직접 커밋·푸시 금지. 푸시와 PR 생성은 사용자 승인 후, 병합은 사용자가 한다.

## 4. 작업 전 조사 (단계 A, 보고만)

1. **자산군 비중 계산**: `rebalance.py`가 4개 자산군 비중을 계산하는 방식(tdf·fund를 bond로 묶는 위치, 현금 포함 여부, 총액 정의)과 `rebalance_threshold`의 의미(절대 %p인지). 엔진이 이 계산을 **수정 없이 import해서 재사용**할 수 있는지.
2. **`withdrawal_strategy` 라우터**: 무엇을 계산하는지(계좌별 인출 순서, 세금 등). 엔진이 계좌 제약(R-07) 참고 정보로 **수정 없이 호출**할 수 있는 순수 함수가 있는지.
3. **연금 관련 계산**(`pension_tax.py` 등): 연금수령한도 등을 인자로 받아 계산하는 순수 함수가 있는지.
4. **시장 데이터**: 기존 데이터(일일 시세 수집, `portfolio_snapshots` 등)로 기준지수나 주식 자산의 고점 대비 하락률을 계산할 수 있는지. 가능하면 방법과 한계를 제안하되, 이번에는 수동 입력을 기본으로 한다.
5. **버킷 재지정 해제**: 인출 설정 그리드에서 버킷 칸을 비우고 저장하면 `holding_profiles.bucket`이 `null`로 저장되는지. 안 되면 원인과 수정 범위를 보고한다.
6. **`decision_log` 현황**: 행 건수, `period` 중복 가능 여부.
7. **`ips_rules` 현재 값**: 규칙 코드별 `parameters` 키 목록(값은 보고해도 된다. 금액이 아님).

**보고 후 중단한다. 승인 전에는 어떤 파일도 만들거나 수정하지 않는다.**

## 5. 판단 엔진 (단계 C)

`backend/decision_engine.py`에 **순수 함수**로 구현한다. 02의 `withdrawal_check` 계산 결과를 입력으로 재사용하고, 같은 계산을 다시 구현하지 않는다.

### 5.0 공통 원칙
- 모든 함수는 기준일 `as_of: date`를 인자로 받는다. 모듈 안에서 `date.today()`를 호출하지 않는다(소스 검사 테스트 포함).
- 분기는 `as_of`로 결정한다(예: 2026-10-05 → `2026-Q4`).
- 규칙 임계값은 `ips_rules`에서 받은 값만 쓴다. 비활성 규칙은 적용하지 않고, 출력에 "비활성으로 미적용"을 표시한다.
- 모든 판단에는 적용 규칙 코드와 근거 데이터(비교한 값과 임계값)를 붙인다.
- 금액은 원 단위 정수로 반올림한다. 반올림 방식은 한 곳에서 정의한다.

### 5.1 입력
- 02 점검 결과: 순인출 필요액(전체·필수), 버킷별 잔액과 연수, 자산 목록(실효 버킷, 자산군, 계좌 유형, 금액), 인출률과 가드레일 상태
- 자산군 목표 비중(`user_config.portfolio.target_*`)과 허용 폭(R-03 방식에 따라 계산)
- 규칙 R-01~R-07의 `parameters`와 `enabled`
- **시장 국면 입력**: 기준지수 이름(선택), 고점 대비 하락률(0~1, 사용자 입력). 입력이 없으면 "정상 국면으로 간주"로 처리하고 이를 출력에 명시한다.

### 5.2 판단 순서

**1단계. 이번 분기 지급액**
- 기본 지급액 = 순인출 필요액(전체) ÷ 4
- R-05 상단 초과면 권고 지급액 = (필수 + 선택 × (1 − `cut_ratio`) − 정기수입) ÷ 4를 함께 제시한다. 필수생활비는 줄이지 않는다.
- R-06 하단 미만이면 증액 여지 = 순인출 필요액 × `raise_ratio` ÷ 4를 **참고로만** 제시한다.
- 엔진의 이후 계산은 기본 지급액을 기준으로 한다. 사용자가 로그 저장 시 실제 적용할 지급액을 선택한다.

**2단계. 지급원**
- 생활비는 **1버킷에서 지급**한다.
- 1버킷 잔액이 지급액보다 적으면 부족분을 "선행 보충 필요"로 표시하고, 3단계 보충 계산에 포함한다.

**3단계. 시장 국면 판정 (R-04)**
- 하락률 ≥ `drawdown_threshold`이면 `downturn`, 아니면 `normal`. 경계값과 같으면 `downturn`.

**4단계. 1버킷 보충 판단 (R-01, R-03, R-04)**
- 지급 후 1버킷 연수 = (1버킷 잔액 − 지급액) ÷ 순인출 필요액
- **정상 국면**
  - 지급 후 1버킷이 `min_years` 미만 → **보충 필수**. 목표량은 `target_years`까지.
  - `min_years` 이상, `target_years` 미만 → 허용 폭을 초과한 자산군(R-03)이 있을 때만 **초과분 범위 안에서 보충**. 없으면 보충하지 않는다.
  - `target_years` 이상 → 보충하지 않는다.
- **하락 국면**
  - 3버킷 자산은 매도 대상에서 **제외**한다(자산군이 초과 상태여도 제외).
  - 지급 후 1버킷이 `min_years` 미만이면 **2버킷에서 `min_years`까지만** 보충한다. 목표(`target_years`)까지 채우지 않는다.
  - `min_years` 이상이면 보충하지 않는다.
  - 2버킷으로도 부족하면 부족액과 함께 "규칙 범위 내 해결 불가, 사용자 판단 필요"로 표시한다. 엔진은 3버킷 매도를 제안하지 않는다.

**5단계. 매도 원천 선택**
- 우선순위
  1. 허용 폭을 초과한 자산군의 자산. 초과가 큰 자산군부터, 자산군의 초과분(현재 금액 − 목표 비중 × 총액)을 한도로 한다.
  2. (정상 국면에서 보충 필수인데 1로 부족할 때) 목표 대비 초과 폭이 큰 자산군 순서
  3. (하락 국면) 2버킷 자산
- 같은 자산군 안에서는 1버킷 자산을 제외하고 금액이 큰 자산부터 선택한다.
- 자산별 매도액은 해당 자산의 `current_value`를 넘지 않는다.

**6단계. 계좌 제약 확인 (R-07)**
- 매도 대상 자산의 `tax_account_type`에 따라 확인 항목을 붙인다.
  - `pension_savings`, `retirement_pension`: 연금수령한도, 사적연금 분리과세 기준, 중도인출 제약
  - `isa`: 의무가입기간, 중도해지 불이익
  - `regular`: 매매차익·배당 과세
- A단계에서 기존 `withdrawal_strategy` 또는 연금 계산 함수를 **수정 없이 호출**할 수 있다고 확인되면, 그 결과를 "참고 정보"로 덧붙인다. 불가능하면 확인 항목만 표시한다.
- 세금 금액을 새로 계산하지 않는다.

**7단계. 결론**
- 결론 유형: `pay_only`(지급만, 보충 없음), `pay_and_refill`(지급 + 보충), `hold`(판단 대상 없음, 예: 순인출 필요액 0), `needs_user_judgment`(규칙 범위 내 해결 불가)
- 보충이 없으면 **"현재는 유지"와 그 이유**(예: 1버킷 2.3년으로 목표 2.0년 이상)를 반드시 출력한다.

### 5.3 출력 구조 (예시, 세부 조정 가능)
```
{
  as_of, period,
  inputs_snapshot: {net_need, buckets, class_weights, targets, bands, rules, market_input},
  payment: {base_quarterly, recommended_quarterly, raise_room_quarterly, source_bucket: 1},
  regime: {status: normal|downturn|assumed_normal, drawdown, threshold},
  refill: {required: bool, reason, target_amount, sells: [{asset_id, asset_name, asset_class, bucket, account_type, amount, rule}]},
  bucket1_after: {years_before_refill, years_after_refill},
  account_checks: [{asset_id, items[]}],
  conclusion: {type, summary_code, reasons[]},
  applied_rules: [...], skipped_rules: [{code, reason}],
  assumptions: [...]
}
```
`summary_code`와 `reasons`는 **코드와 수치**로 반환한다. 사람이 읽는 문장은 화면에서 만든다(06의 AI 설명과 분리하기 위함).

### 5.4 테스트 (pytest, `as_of` 고정, 운영 DB 사용 금지)
- 정상 국면: 1버킷 min 미만 → 보충 필수, 목표까지 / min~target 사이 + 초과 자산군 있음 → 초과분 한도 보충 / min~target 사이 + 초과 없음 → 유지 / target 이상 → 유지
- 하락 국면: 3버킷이 초과 자산군이어도 매도 제외 / min 미만 → 2버킷에서 min까지만 / 2버킷 부족 → `needs_user_judgment`
- 경계값: 하락률 = 임계값, 연수 = min_years, 연수 = target_years
- 가드레일: 상단 초과 시 권고 지급액(필수 불변), 하단 미만 시 증액 여지(기본 지급액 불변)
- 1버킷이 지급액보다 적은 경우의 선행 보충
- 자산별 매도액이 잔액을 넘지 않음, 1버킷 자산이 매도 대상에서 제외됨
- R-03 두 모드(config, relative + min_abs)
- 규칙 비활성화 시 미적용 표시
- 시장 입력 없음 → `assumed_normal`
- 순인출 필요액 0 → `hold`

## 6. API (단계 D)

| 경로 | 메서드 | 내용 |
|---|---|---|
| `/ips-rules` | GET | 전체 규칙 |
| `/ips-rules/{rule_code}` | PUT | `parameters`, `enabled` 수정. 규칙별 검증(아래) |
| `/decision-engine/run` | POST | 본문: `market_input`(선택), `as_of`(선택). 판단 결과 반환. **DB에 쓰지 않는다.** |
| `/decision-log` | GET | 목록(최신순) |
| `/decision-log` | POST | 판단 결과 저장. 본문: 엔진 출력 전체, 사용자가 선택한 지급액 |
| `/decision-log/{id}` | PATCH | `executed`, `deviation_reason` 수정 |

**규칙 검증**
- R-01: 0 < `min_years` ≤ `target_years`
- R-02: `target_years` > 0
- R-03: `mode` ∈ {config, relative}. relative면 0 < `relative` ≤ 1, 0 ≤ `min_abs` ≤ 1
- R-04: 0 < `drawdown_threshold` < 1
- R-05: `upper_multiplier` > 1, 0 < `cut_ratio` < 1
- R-06: 0 < `lower_multiplier` < 1, 0 < `raise_ratio` < 1
- 알 수 없는 키는 거부한다. `rule_code`, `category`는 수정할 수 없다.

**로그 규칙**
- 같은 `period`에 이미 기록이 있으면 POST는 409를 반환한다. 화면에서 "덮어쓰기"를 확인받은 경우에만 `?overwrite=true`로 교체한다. (스키마 변경 없이 API에서 보장)
- `executed=false`이면 `deviation_reason`이 필수다.
- 저장 시 `engine_output`에는 엔진 출력 전체와 입력 스냅샷을 담는다. 나중에 입력값이 바뀌어도 당시 판단을 재현할 수 있어야 한다.

**R-03 파라미터 변경**: 현재 R-03은 `{}`다. `{"mode": "config"}`로 바꾸는 SQL을 B단계에서 작성하고, 사용자가 적용한다. 엔진은 `{}`도 `config`로 해석해 하위 호환을 유지한다.

## 7. 화면 (단계 E)

### 7.1 인출 설정 → "규칙" 탭 (6번째 탭)
- 규칙별 카드: 이름, 설명, 활성 토글, 파라미터 입력
- 비율은 %로 입력·표시하고 0~1로 저장한다(01의 변환 함수 재사용). 연수는 "년", 배수는 "배"로 표시한다.
- R-03은 방식 선택(기존 설정값 사용 / 목표 대비 상대 폭). "기존 설정값 사용"이면 현재 `rebalance_threshold` 값을 읽기 전용으로 보여 주고 설정 화면 링크를 둔다.
- 저장 전 검증 오류를 필드별로 표시한다.
- 상단 문구: "기본값은 예시입니다. 본인의 재정 상황에 맞게 조정하세요."

### 7.2 신규 메뉴 "분기 인출 판단" (NAV_GROUPS의 연금·세금 그룹에 추가)
- **입력 영역**: 기준지수 이름(선택), 고점 대비 하락률(%) 입력, "판단 실행" 버튼. 입력하지 않으면 "정상 국면으로 간주" 안내.
- **결과 영역**
  - 결론 한 줄 (예: "이번 분기: 1버킷에서 ○○원 지급, 보충 없음 — 현재는 유지")
  - 지급: 기본 지급액, (해당 시) 가드레일 권고 지급액과 증액 여지
  - 국면 판정: 입력 하락률, 임계값, 결과
  - 보충: 필요 여부와 이유, 매도 목록(자산, 자산군, 버킷, 계좌, 금액, 근거 규칙)
  - 1버킷 연수: 보충 전 → 보충 후
  - 계좌 확인 항목
  - 적용 규칙과 비활성 규칙, 가정 목록
  - 문구: "규칙에 따른 판단 결과이며, 실행 여부는 직접 결정하세요."
- **저장**: 적용할 지급액(기본/권고) 선택 후 "판단 기록 저장". 같은 분기 기록이 있으면 덮어쓰기 확인.
- **기록 목록**: 분기별 결론, 지급액, 실행 여부 표시. 행에서 "실행함 / 다르게 실행함"을 선택하고, 다르게 실행했으면 사유를 입력한다.

### 7.3 공통
- 사람이 읽는 문장은 `summary_code`와 `reasons`로 프론트에서 조립한다. 문장 조립 함수는 한 곳에 두고 단위 테스트를 추가한다.
- 기존 컴포넌트와 스타일을 재사용한다.
